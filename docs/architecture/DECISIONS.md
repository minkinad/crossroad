# Architecture decisions

1. **Two explicit data modes.** GitHub Pages serves a static demo. Production-like account flows require an API and PostgreSQL. The mode switch lives in `apps/web/src/lib/index.ts`; browser-only writing is visibly labeled.
2. **Shared validation at the boundary.** `packages/contracts` contains Zod write schemas. The API validates again regardless of frontend behavior. Article bodies remain plain text and React escapes them, avoiding an HTML sanitization problem until a structured editor exists.
3. **JWT access plus opaque refresh.** The API issues 15-minute access JWTs in JSON; the web keeps them in memory. A random refresh token is hashed in `Session`, rotated atomically, and stored in an HttpOnly SameSite cookie. A five-second collision window lets another tab retry a recent rotation without revoking the session; reuse after that window revokes it. Access JWTs bind to an active session, so revocation takes effect immediately. Cookie-dependent auth mutations require the configured Origin. The in-memory auth rate limiter is suitable for one process only; distributed deployment needs a shared limiter.
4. **PostgreSQL and Prisma 6.** Prisma 6 is pinned for stable generated-client behavior on Node 22. The SQL migration adds a GIN full text expression index. Searches use parameterized SQL for ranking, then Prisma to hydrate bounded results.
5. **No automatic legacy import.** Old localStorage posts only have unverified display names. They can be exported with schema checks but are never uploaded or assigned to an account implicitly. The current demo key can also be exported raw, including when its structure is invalid, before any user decides to repair it.
6. **Small vertical slice first.** Plain text drafts, flat comments, and simple bookmarks are complete enough to verify from browser to database. Rich text, nested discussions, collections, discovery ranking, moderation, and profiles require separate schema and UX work.
